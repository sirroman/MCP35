# Регресс-тесты INFATON MCP для тестовой 1С

Статус: утвержденный набор. Использовать после каждого изменения кода расширения INFATON MCP; имена и UUID зависимостей каждого запуска подтверждать заново по метаданным и данным тестовой базы.

## Цель

Проверять после каждого изменения кода расширения INFATON MCP:

- честность результата записи: нет `success:true`, если значение не сохранилось;
- создание, чтение, изменение, проведение и удаление/пометку удаления тестовых объектов;
- корректную обработку ссылок, перечислений, скаляров и табличных частей;
- типовые операции: физлицо, контрагент, договор контрагента, счет покупателю, банковская выписка.

## Общие правила

1. Выполнять только в тестовой базе и сначала проверить `get_server_info`.
2. Все создаваемые объекты именовать с префиксом `Регресс тест MCP <run-id>`; для документов использовать `Комментарий` с этим текстом.
3. Перед изменением существующего объекта сохранять полный снимок `get_object_by_ref`.
4. После каждой записи выполнять `get_object_by_ref`; `success:true` без сохраненного значения — FAIL.
5. Для битой ссылки использовать случайный ненулевой UUID. Нулевой UUID не использовать как «несуществующий объект».
6. Ссылки передавать как `<Реквизит>_guid`; очистку проверять через реальное имя реквизита и `null`.
7. После теста: распровести документы, установить `ПометкаУдаления=true` (если физическое удаление не предоставлено MCP), затем контрольным запросом убедиться, что активных объектов с префиксом запуска не осталось.
8. Любая неубранная запись — FAIL всего прогона.

## Набор данных запуска

- `RUN_NAME`: `Регресс тест MCP YYYYMMDD-HHMMSS`.
- `BAD_GUID`: случайный ненулевой UUID, отсутствие подтверждено контрольным чтением/запросом.
- Организация, валюта, номенклатура, ставка НДС и иные обязательные ссылки выбираются из существующих тестовых данных после проверки метаданных.

## A. Контракт записи ссылок

| ID | Действие | Ожидается |
|---|---|---|
| A1 | `update_object`: существующая ссылка через `_guid` | `success:true`, контрольное чтение содержит нужный GUID |
| A2 | `update_object`: `BAD_GUID` через `_guid` | `success:false`, `attribute_errors`; прежнее значение не изменено |
| A3 | `update_object`: GUID объекта неверного типа | `success:false`, `attribute_errors`; прежнее значение не изменено |
| A4 | `update_object`: ссылка без `_guid` | либо корректное сохранение, либо явная ошибка; тихий успех запрещен |
| A5 | очистка ссылки через `null` | поле пустое при контрольном чтении |
| A6 | `set_attribute` для ссылки | сохранение или явная ошибка согласно контракту; тихий успех запрещен |

## B. Табличные части

| ID | Действие | Ожидается |
|---|---|---|
| B1 | `replace` с корректной ссылкой | строка создана, ссылка и скаляры сохранены |
| B2 | `append` с корректной ссылкой | добавлена ровно одна строка |
| B3 | `update_by_index` с корректной ссылкой | изменена указанная строка |
| B4 | любой режим с `BAD_GUID` | `success:false`, `attribute_errors.context` указывает верную строку |
| B5 | смешанная строка: валидный скаляр + битая ссылка | операция атомарна: `success:false`, вся строка и ТЧ полностью равны снимку до вызова; частичная запись — критический FAIL |

## D. Контрагент и договор

| ID | Действие | Ожидается |
|---|---|---|
| D1 | создать контрагента с именем запуска | объект создан и читается обратно |
| D2 | изменить подтвержденные скалярные поля контрагента | значения сохранены |
| D3 | создать договор контрагента с `Владелец_guid` тестового контрагента | договор создан, владелец имеет правильный GUID |
| D4 | изменить название/номер/дату договора | значения сохранены |
| D5 | заменить ссылку договора на битый/неверный тип | явная ошибка, прежний владелец сохранен |
| D6 | пометить договор и контрагента на удаление | обе пометки сохранены, активных тестовых элементов нет |

## E. Счет покупателю

| ID | Действие | Ожидается |
|---|---|---|
| E1 | создать `Документ.СчетНаОплатуПокупателю` с комментарием запуска, организацией, контрагентом и договором | документ создан, все ссылки сохранены |
| E2 | заполнить подтвержденную ТЧ услуг/товаров | строки и суммы читаются обратно |
| E3 | изменить комментарий, сумму/строку | изменены только целевые поля |
| E4 | изменить `ДоговорКонтрагента_guid` на другой корректный тестовый договор | ссылка сохранена |
| E5 | записать `BAD_GUID` в договор | `success:false`, прежний договор сохранен |
| E6 | провести и прочитать | `Проведен=true` либо документированная бизнес-ошибка валидации |
| E7 | распровести и пометить на удаление | `Проведен=false`, `ПометкаУдаления=true` |

## G. Создание с ошибками и смежные пути

| ID | Действие | Ожидается |
|---|---|---|
| G1 | `create_object` с корректной ссылкой | `success:true`, GUID и сохраненная ссылка |
| G2 | `create_object` с битой ссылкой | `success:false`, `attribute_errors`, GUID возвращен, скаляры сохранены |
| G3 | перечисление по внутреннему имени | значение сохранено |
| G4 | скаляры: строка, число, дата, boolean | значения сохранены без `attribute_errors` |
| G5 | `simulate_fill_on_basis` на подтвержденной цепочке | dry-run без записи и ошибки |
| G6 | `fill_on_basis` на подтвержденной цепочке | объект создан, прочитан и помечен на удаление |

## H. Итоговая уборка

1. Найти все объекты текущего запуска по `RUN_NAME`/комментарию.
2. Распровести созданные документы.
3. Установить `ПометкаУдаления=true` всем созданным документам и справочникам в порядке зависимостей: выписки/счета -> договоры -> контрагенты/физлица.
4. Контрольным чтением подтвердить пометки.
5. Запросом подтвердить: активных объектов запуска (`НЕ ПометкаУдаления`) — 0.

## Критерий релиза

- Все обязательные кейсы PASS.
- Нет тихого успеха при несохраненном значении.
- Нет активных тестовых объектов после уборки.
- BLOCKED или непроверенный обязательный кейс означает, что готовность к продуктиву не подтверждена.
