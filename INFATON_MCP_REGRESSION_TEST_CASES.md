# Регресс-тесты INFATON MCP для тестовой 1С

Статус: утвержденный набор. Использовать после каждого изменения кода расширения INFATON MCP; имена и UUID зависимостей каждого запуска подтверждать заново по метаданным и данным тестовой базы.

## Цель

Проверять после каждого изменения кода расширения INFATON MCP:

- честность результата записи: нет `success:true`, если значение не сохранилось;
- создание, чтение, изменение, проведение и удаление/пометку удаления тестовых объектов;
- корректную обработку ссылок, перечислений, скаляров и табличных частей;
- типовые операции: физлицо, контрагент, договор контрагента, счет покупателю, банковская выписка.

## Общие правила

1. Выполнять только в тестовой базе и сначала проверить `get_server_info`.
2. Все создаваемые объекты именовать с префиксом `Регресс тест MCP <run-id>`; для документов использовать `Комментарий` с этим текстом.
3. Перед изменением существующего объекта сохранять полный снимок `get_object_by_ref`.
4. После каждой записи выполнять `get_object_by_ref`; `success:true` без сохраненного значения — FAIL.
5. Для битой ссылки использовать случайный ненулевой UUID. Нулевой UUID не использовать как «несуществующий объект».
6. Ссылки передавать как `<Реквизит>_guid`; очистку проверять через реальное имя реквизита и `null`.
7. После теста: распровести документы, установить `ПометкаУдаления=true` (если физическое удаление не предоставлено MCP), затем контрольным запросом убедиться, что активных объектов с префиксом запуска не осталось.
8. Любая неубранная запись — FAIL всего прогона.

## Набор данных запуска

- `RUN_NAME`: `Регресс тест MCP YYYYMMDD-HHMMSS`.
- `BAD_GUID`: случайный ненулевой UUID, отсутствие подтверждено контрольным чтением/запросом.
- Организация, валюта, номенклатура, ставка НДС и иные обязательные ссылки выбираются из существующих тестовых данных после проверки метаданных.

## H. CDC: `get_changes_since` (инкрементальный опрос и пагинация)

Раздел предназначен для выполнения ИИ-агентом. Конкретных дат и времени в кейсах нет — все точки отсчёта берутся **из ответов сервера** в ходе прогона.

### Правила для агента

1. **Не использовать собственные часы** для `since`: часы агента и сервера 1С могут расходиться. Единственный источник меток — поля `watermark` и `timestamp` из ответов MCP.
2. **Передавать `watermark` в следующий `since` строго без изменений.** Ручное прибавление секунды, округление или сдвиг часового пояса запрещены — такой обход маскирует дефект и делает кейс недействительным.
3. Метка запуска `CDC_RUN` = `CDC-QA-<текущие дата и время старта прогона, YYYYMMDD-HHMMSS>`; ставится в `Комментарий` всех создаваемых документов.
4. Тестовый тип: `Документ.СчетНаОплатуПокупателю` (или другой подтверждённый по метаданным документ). Документы создаются пустыми/минимальными и **не проводятся**, если кейс не требует иного.
5. Между шагами, где нужен порядок событий во времени, выдерживать паузу не менее 2 секунд (иначе события могут попасть в одну секунду там, где кейс этого не требует).
6. **Детектор зацикливания при пагинации:** страница N+1 запрошена с `since` = `watermark` страницы N, обе с `truncated=true`, и у них одинаковый `watermark` и одинаковый набор GUID — FAIL (бесконечный цикл). Сравниваются только страницы одного обхода; повторы запроса с прежним `since` детектор не учитывает. Ограничение безопасности: не более 20 страниц на один обход; превышение — FAIL.
7. **Обход всех страниц (drain)** — это цикл: вызвать `get_changes_since`, накопить `changes`, при `truncated=true` повторить с `since = watermark`, остановиться на `truncated=false`. Результат обхода — объединение GUID всех страниц.
8. Перед записью каждого документа сохранять `watermark` последнего ответа как именованную метку (`W0`, `W1`, …) — все последующие проверки ссылаются на эти метки, а не на время.
9. **Страница с `truncated=true` — промежуточное состояние, а не результат.** Вердикт по кейсу с пагинацией выносится только когда обход завершён (`truncated=false`) или сработал детектор зацикливания/лимит 20 страниц. Статусы кейса:
   - `PASS` — обход завершён, все ожидания выполнены;
   - `FAIL` — только по критериям из колонки «Ожидается» или разделу «Недопустимо»;
   - `НЕ ЗАВЕРШЁН` — обход прерван до `truncated=false` (не FAIL и не PASS); кейс перезапускается от той же метки, а если после неё были новые изменения — от свежей метки;
   - `SKIPPED` — условие кейса не воспроизвелось (см. H9).
10. **Строгий порядок:** H1 → H11. H6–H8 выполняются до любых новых изменений (H9, H10). Дополнительные проверки вне сценария не засчитываются в H6–H8; для них берётся своя свежая метка и обход доводится до конца.
11. **Протокол каждой страницы в отчёте:** `since`, `max_results`, `count`, GUID страницы, `watermark`, `truncated`. К протоколу прикладывается **дословный JSON каждого ответа** (копия, а не перепечатка — ошибка в одной цифре метки выглядит как зацикливание). Без протокола и JSON вердикт FAIL по пагинации не ставится.
12. **Изоляция.** Уборка прошлых прогонов и любые записи вне сценария выполняются **до H1 или после H11**. Любая запись в тестовый тип во время раздела H (в том числе пометка «забытого» документа) добавляет событие в окно и меняет ответы; затронутые кейсы получают статус `НЕ ЗАВЕРШЁН` и перезапускаются со свежей метки.
    - Старые активные тестовые документы сами по себе H1 **не блокируют**: CDC реагирует на изменения, а не на существование объектов, и кейсы проверяют только GUID текущего запуска. Блокирует только запись во время H.
    - Проверка перед H1 и в разделе I выполняется контрольным запросом `execute_query` (см. «Контрольные запросы» в разделе I), а не списком документов по дате: `get_document_list` фильтрует по дате документа и отсутствия объектов не доказывает.
13. **Проверка инварианта на каждой странице** (сравнение ISO-строк допустимо):
   - `truncated=true` ⇒ `watermark` **строго больше** `since`. Нарушение, подтверждённое дословным JSON, — критический FAIL.
   - `truncated=false` ⇒ обход завершён; `watermark` равен текущему времени сервера на момент вызова (не обязан совпадать с временем изменений).
14. **После `truncated=false` обход закончен.** Повторный запрос с тем же `since` в обход не входит; одинаковый ответ на одинаковый вход — ожидаемое поведение, а не цикл. Разный ответ на одинаковый `since` означает, что между вызовами появились новые события (см. п. 12).

| H5 | Изменить у B дату документа на дату ≥ 7 дней в прошлом (от даты документа, прочитанной через `get_object_by_ref`) и `Комментарий`. Запрос `since = W1`. | GUID B присутствует как `updated`; контрольное чтение подтверждает старую дату документа. CDC отбирает изменения по **времени записи**, а не по дате документа. |
| H6 | **Пагинация, `max_results=1`** (исходный дефект). Drain от `since = W0` с `max_results=1`. | Обход завершается с `truncated=false` не более чем за 20 страниц; детектор зацикливания не сработал; объединение GUID содержит **и A, и B**. `watermark` при `truncated=true` строго растёт от страницы к странице. Повтор той же страницы с тем же `watermark` — **критический FAIL** (потребитель зависает или теряет B). |
| H7 | Контроль без малого лимита: запрос `since = W0`, `max_results=5000`. | Один ответ, `truncated=false`, содержит A и B. Множество GUID запуска совпадает с объединением из H6. |

| H9 | **Несколько объектов в одной секунде.** Сохранить `W2` = свежий `watermark`. Создать счета C, D, E максимально быстро подряд (без пауз). Прочитать `timestamp` их событий запросом `since = W2`, `max_results=5000`. Если хотя бы два из них имеют одинаковый `timestamp` — выполнить drain от `W2` с `max_results=1`. Если совпадений нет — повторить попытку (до 3 раз, каждый раз с новой тройкой счетов); если так и не удалось — пометить кейс `SKIPPED (не воспроизведено)`, это не PASS. | Drain завершается без зацикливания; объединение содержит C, D, E. Первая страница с A, `truncated=true` и `watermark` > `W3` — нормальное промежуточное состояние, обход продолжается до `truncated=false`. |
| H11 | Устойчивость к повторам: после завершения всех кейсов выполнить drain от `W0` дважды подряд. | Оба обхода возвращают одинаковое множество GUID запуска; второй обход не теряет ни одного GUID. |

### Допустимое и недопустимое поведение

- **Допустимо:** повтор GUID на стыке финальной страницы (`truncated=false`, её `watermark` включителен) и следующего опроса — потребитель отсеивает дубли по GUID.
- **Допустимо:** `count > max_results`, если несколько объектов изменены в одну секунду (секунда не делится между страницами).
- **Нормально:** страница с `truncated=true`, у которой `watermark` строго больше `since`, — обход надо продолжить, это не дефект. При `truncated=true` `watermark` обычно равен времени последнего выданного изменения + 1 секунда.
- **Недопустимо:** одинаковый `watermark` на двух подряд страницах с `truncated=true`; необходимость вручную сдвигать `watermark`; отсутствие в объединении обхода GUID, который присутствует в контрольном запросе H7.
- **Ограничение API (не дефект):** возвращается последнее изменение на GUID, а не цепочка `created → updated`; восстановить все промежуточные события за интервал этим методом нельзя.

### Уборка раздела H

Все счета с `Комментарий` начинающимся на `CDC_RUN` помечаются на удаление (не проводятся); контрольный запрос — 0 активных объектов с меткой запуска.

## I. Итоговая уборка

1. Найти все объекты текущего запуска по `RUN_NAME`/комментарию.
2. Распровести созданные документы.
3. Установить `ПометкаУдаления=true` всем созданным документам и справочникам в порядке зависимостей: выписки/счета -> договоры -> контрагенты/физлица.
4. Контрольным чтением подтвердить пометки.
5. Запросом подтвердить: активных объектов запуска (`НЕ ПометкаУдаления`) — 0.

**Трогать можно только объекты тестов:** `Комментарий`/наименование с префиксом `Регресс тест MCP` или `CDC-QA-`, либо GUID из отчётов прошлых прогонов. Массовая пометка «всех документов за период» запрещена — это чужие данные базы, от которых зависят другие кейсы (например, группа F).

### Контрольные запросы (`execute_query`)

Поле `Комментарий` — строка неограниченной длины, поэтому в условии её приводят к ограниченной через `ВЫРАЗИТЬ`. Для другого типа документа/справочника меняется только имя таблицы; у справочников вместо `Комментарий` проверяется `Наименование`.

**Активные тестовые объекты** (перед H1 и в конце прогона ожидается 0 строк):

```
ВЫБРАТЬ
    Т.Ссылка, Т.Номер, Т.Дата, ВЫРАЗИТЬ(Т.Комментарий КАК СТРОКА(200)) КАК Комментарий
ИЗ
    Документ.СчетНаОплатуПокупателю КАК Т
ГДЕ
    НЕ Т.ПометкаУдаления
    И (ВЫРАЗИТЬ(Т.Комментарий КАК СТРОКА(200)) ПОДОБНО "CDC-QA-%"
       ИЛИ ВЫРАЗИТЬ(Т.Комментарий КАК СТРОКА(200)) ПОДОБНО "Регресс тест MCP%")
```

**Проверка на лишнее** — помеченные на удаление документы БЕЗ тестовой метки (ожидается 0 строк; найденные — кандидаты на снятие пометки после ручной сверки):

```
ВЫБРАТЬ
    Т.Ссылка, Т.Номер, Т.Дата, ВЫРАЗИТЬ(Т.Комментарий КАК СТРОКА(200)) КАК Комментарий
ИЗ
    Документ.СчетНаОплатуПокупателю КАК Т
ГДЕ
    Т.ПометкаУдаления
    И НЕ ВЫРАЗИТЬ(Т.Комментарий КАК СТРОКА(200)) ПОДОБНО "CDC-QA-%"
    И НЕ ВЫРАЗИТЬ(Т.Комментарий КАК СТРОКА(200)) ПОДОБНО "Регресс тест MCP%"
```

## Критерий релиза

- Все обязательные кейсы PASS.
- Нет тихого успеха при несохраненном значении.
- Нет активных тестовых объектов после уборки.
- BLOCKED или непроверенный обязательный кейс означает, что готовность к продуктиву не подтверждена.
